# A6.1 Tapestry connector

The connector gives a teammate's Claude the Tapestry protocol and its list tools in one place: guidance read live from the written sources, and tools that read, check and draft lists with the same code Brainstorm's List Management runs. It is team-only in v1. Where its code runs is decided in `engineering-team/decisions/tapestry-connector/0001-where-the-connector-runs.md`: inside Loom's existing connector, behind a `tapestry` scope of its own, using a pinned build of Brainstorm-UI's list code. The stories below follow from that decision.

## The problem

What a Claude needs to know to build on Tapestry is spread across:

- `BIBLE.md` in this repo, the onboarding doc for agents, about 2,000 lines;
- the drafts in this repo's `protocols/drafts/`, and the published specs, `CONCEPTS.md` and `ECOSYSTEM.md` in NosFabrica/protocols;
- Brainstorm-UI's `docs/dictionary/`: how lists present, house copies, building lists with Claude;
- Brainstorm-UI's list code (`listCheck`, `listDraft`, `listPrompt`, `listImport`, `dictionaryConcepts`), where some rules exist only as code;
- the process the team follows to build a list (candidate items first, a checked header, review, signing, a pilot, a verified import), which is written down nowhere in full.

Each Claude session carries its own copy of whatever it read, and the copies drift. Local checkouts of this repo hold Bibles from March to June, all older than the one on its branches. A Claude opened in another repo starts with none of it. And a rule a Claude reads as prose, it can misread; a rule a checker enforces, it cannot.

## Who it is for

The team's Claudes, in Claude Code and in Claude chat, acting for a teammate who builds or reviews a list, or who needs the protocol to build a feature. v1 is for the team only. Later the protocol layer opens to outside curators and their agents, without the team's own process.

## What it does

1. **Guidance by topic.** A guide tool lists the topics and serves one at a time, read from its source when asked, so an edit on the source's branch shows up on the next call: the Bible by section, each protocol draft and spec by name, Brainstorm-UI's dictionary docs, and the team's list process. Nothing is loaded whole into a session.
2. **Reads.** Headers, items, the Dictionary and URL templates, from the dcosl relay and the search relay.
3. **Checks and drafts.** A header or an item checked by Brainstorm-UI's `listCheck`, with the results List Management shows; a header or items drafted as unsigned events. The connector holds no key and publishes nothing: signing stays with a person, in List Management or their own signer.
4. **Sign-in for the team only,** in Claude Code and in Claude chat.

## What done looks like

A teammate's Claude with only the connector builds a header and five items that pass `listCheck` with zero header problems, from guidance it read through the connector, and an edit to the Bible or a draft on its source branch shows up on the next call.

## Out of scope

- Signing or publishing anything, or holding any key.
- Search tools for agents. They belong to the agent and partner milestone and wait on the interpretation schema.
- The local Tapestry stack: a person's own Neo4j, firmware and control panel.
- Opening the connector to people outside the team. The ADR says how that happens later.
- Changing the protocol. The connector serves what its sources say.

## Notes

- **Each source names its branch.** This repo's `main` and `staging` have diverged, so the branch a topic is read from is a setting per source, never an assumption.
- **Reads cost requests.** Sources come from GitHub, against a request budget the team's account shares, so a topic is cached for minutes and fetched again once stale.

## Stories

### A6.1.a Build Brainstorm-UI's list code as one ES module
- repo: NosFabrica/Brainstorm-UI

A build target, such as Vite's library mode, that writes `listCheck`, `listDraft`, `listPrompt`, `listImport` and `dictionaryConcepts`, with what they import and the config they read, into one ES module that runs in Node. The `@/` aliases are resolved, and the caller supplies the env that `runtimeEnv` reads in the browser. A test runs the built module's `listCheck` on the existing fixtures and expects the results the source gives, and CI builds it, so a change that breaks the build fails there. Done when a Node script outside Brainstorm-UI imports the built file and checks a header and an item.

### A6.1.b Write the team's list process down
- kind: record
- repo: nousclawds4/loom

The process the team follows to build a list, in one private file in Loom's repo: candidate items first, the header drafted and checked, the team's review, who signs what, curator keys, a pilot before a full import, and the counts checked after it. What belongs to the protocol or to Brainstorm's conventions links to its own doc rather than repeating it; anything missing there becomes a follow-up in that doc's repo. Done when the file is on Loom's main and a teammate has read it against the last lists the team built.

### A6.1.c The tapestry scope
- repo: nousclawds4/loom

A `tapestry` scope beside the board's two levels: in the scopes Loom's OAuth supports, as a box on the consent page beside the level, and on the pages that show a connection. A Tapestry tool checks for the scope itself and refuses without it, naming the scope and how to reconnect. A connection made before the scope existed has no Tapestry access until its person reconnects, and the board's level check is unchanged. The consent page and the connect steps were rewritten recently for the two levels, so this story's changes there are checked against that work before it starts. Done when a connection with the scope reaches a stub Tapestry tool and one without it is refused.

### A6.1.d Guide topics from their sources
- repo: nousclawds4/loom
- depends_on: A6.1.c

A `tapestry_guide` tool that lists the topics and serves one, read when asked. A config names each source: its repo, path and branch, and how it splits into topics (`BIBLE.md` by its `##` sections; the protocol drafts and specs, Brainstorm-UI's dictionary docs and the team's list process by file). Reads go through Loom's GitHub client, under its request budget, and a topic is cached for minutes. The loader is separate from the one that reads Loom's own CLAUDE.md, with tests of its own. Done when the guide serves a Bible section, a protocol draft and a dictionary doc, and an edit on a source's branch shows up once its cache expires.

### A6.1.e Read tools for lists
- repo: nousclawds4/loom
- depends_on: A6.1.c

Tools that read a list's header and items, the Dictionary's concepts and the URL templates, from the dcosl relay and the search relay, and return them as events with the relay each came from. Read-only and behind the scope. Done when a Claude reads a filed list's header, ten of its items and the URL templates its header names.

### A6.1.f Check and draft tools on the pinned build
- repo: nousclawds4/loom
- depends_on: A6.1.a, A6.1.c, A6.1.e

Loom takes the module A6.1.a builds at a named Brainstorm-UI commit, records that commit, and moves to a newer one only by pull request. Tools check a header and an item with its `listCheck`, with the results List Management shows, and draft a header or items as unsigned events. Nothing is signed or published. Done when the tools report the same problems as `npx vite-node` at the same Brainstorm-UI commit, on a good list and on a broken one.

### A6.1.g Acceptance: a list built through the connector
- kind: record
- repo: nousclawds4/loom
- depends_on: A6.1.b, A6.1.d, A6.1.f

The spec's done-when, run and written down. A teammate's Claude in Claude chat, with only the connector, builds a header and five items that pass `listCheck` with zero header problems, from guidance it read through the connector; and an edit to the Bible or a draft on its source branch shows up on the next call after the cache. Done when the record is on Loom's main with what was run and what came back.
